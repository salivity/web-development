How to Identify and Fix Flaky Automated Tests

Flaky automated tests—tests that intermittently pass and fail without changes to the underlying code—erode developer trust, slow down CI/CD pipelines, and disguise genuine regressions. This guide outlines actionable strategies for web development engineers to systematically detect non-deterministic test behavior, isolate root causes such as race conditions and shared state, and implement architectural fixes to maintain a robust, reliable test suite.

Detecting and Tracking Flaky Tests

Before you can eliminate flaky tests, you must reliably surface them:

  • Stress Execution (Repetition Testing): Run suspect test suites in a loop (e.g., 50 to 100 times) within a pull request or a dedicated CI job to reveal intermittent failures before code reaches production.
  • Test Quarantine Workflows: Automatically route failing tests with inconsistent historical results into a quarantined, non-blocking pipeline. This prevents CI bottlenecks while ensuring the offending tests remain tracked and visible to the team.
  • Automated Failure Analytics: Integrate CI test reporters that aggregate pass/fail ratios over time. Metrics such as execution duration variance and failure distribution across environments highlight fragile tests faster than manual review.

Eliminating Asynchronous Race Conditions

Asynchronous behavior in modern single-page applications is the leading cause of non-deterministic end-to-end (E2E) and integration tests.

  • Eliminate Arbitrary Sleep Calls: Never use hardcoded timeouts like sleep() or waitForTimeout(). Network latency and CPU throttling in CI environments make static delays unpredictable.
  • Rely on Dynamic, Deterministic Assertions: Use framework-native auto-waiting mechanisms (such as Playwright’s auto-wait or Cypress’s built-in retry assertions) that poll the DOM until the desired element is visible, actionable, or contains expected values.
  • Wait for Network Idle or Specific API Responses: Explicitly intercept and await target network responses rather than waiting for UI rendering alone. This guarantees that background operations complete before assertions execute.

Enforcing Strict Test Isolation

Shared state between test runs introduces side-effects that cause downstream tests to fail unpredictably depending on execution order.

  • Clean Storage and Cookies: Reset cookies, localStorage, sessionStorage, and IndexedDB before each test case runs.
  • Isolate Database State: Use isolated database transactions, dedicated database tenants, or automated rollback scripts between tests. Alternatively, generate unique IDs or test-specific fixtures dynamically using factory libraries rather than relying on static, shared seed data.
  • Randomize Execution Order: Run tests in a randomized order locally and in CI to quickly expose hidden dependencies where one test inadvertently prepares data for another.

Stabilizing the Execution Environment

Discrepancies between local development machines and shared CI runners frequently trigger unexpected timeouts and rendering discrepancies.

  • Containerize Test Runners: Use standardized Docker images for running headless browsers to eliminate operating system, font rendering, and browser version mismatches.
  • Mitigate Resource Contention: Headless browsers are memory- and CPU-intensive. Limit parallel test execution to match the assigned vCPUs on CI agents, and allocate sufficient shared memory (/dev/shm) to prevent browser crashes.
  • Mock Flaky External Dependencies: Avoid connecting to third-party services, analytics endpoints, or payment gateways during automated test runs. Use network interception to stub third-party APIs with predictable, deterministic responses.
